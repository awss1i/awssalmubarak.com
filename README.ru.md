Исходный код моего личного сайта. Это статический сайт (static site) без фреймворка и без
зависимостей (dependency) во время выполнения. Его генерирует небольшой пайплайн (pipeline) на
стандартной библиотеке Python. Страница вкладов работает плавно, будь в ней двадцать принятых
пулреквестов (merged pull request) или двадцать тысяч, а страница проектов (builds) запускает
предпросмотр только тех проектов, на которые вы смотрите, сколько бы их там ни было.

---

## <a id="the-virtualized-ledger"></a>Виртуализированный реестр

Страница вкладов служит реестром вкладов (contributions ledger), где собраны все мои принятые
пулреквесты. При том масштабе, к которому я стремлюсь, это десятки тысяч строк, поэтому здесь
используется виртуализированный список (virtualized list), написанный вручную на чистом JavaScript.
В DOM находятся только строки рядом с областью просмотра (viewport), пулреквесты репозитория
создаются только тогда, когда вы его раскрываете, а поиск использует дебаунс (debounce) и фильтрует
данные, вместо того чтобы перестраивать страницу при каждом нажатии клавиши.

Вот что это даёт в сравнении с версией, которая рендерит все строки сразу, на 2500 репозиториях и
13 724 принятых пулреквестах:

| | Наивная реализация (рендерит всё) | Виртуализированный список (этот сайт) |
|---|---|---|
| Узлы DOM | 127 306 | 281 |
| Повторный рендеринг (re-render) одной сортировки | 279 мс | 3 мс |
| Время до интерактивности (time to interactive) | 534 мс | 312 мс |

Верить этим числам на слово не нужно. `bench/` заново получает их на вашем собственном компьютере,
подробности описаны в [бенчмарке](bench/README.ru.md).

## <a id="the-builds-page"></a>Страница проектов

Страница проектов показывает каждый мой инструмент с предпросмотром в окне, по виду которого
понятно, что это за проект. Инструмент командной строки работает в терминале, а сайт работает
вживую в окне браузера. Если нажать на предпросмотр, он откроется в большом размере. На компьютере
заголовок остаётся на месте, а под ним прокручиваются только проекты.

Живой предпросмотр (live preview) является целой веб-страницей, поэтому страница с такими
предпросмотрами быстро становится тяжёлой. Собственная ленивая загрузка (lazy loading) браузера
решает только, когда начать загрузку. Она ничего не выгружает, а для видео ленивой загрузки
в браузерах нет совсем. Поэтому страница проектов загружает предпросмотры через планировщик медиа
(media scheduler), написанный на чистом JavaScript.

- Каждый предпросмотр сначала показывает статичное изображение (still image).
- Предпросмотр становится живым, когда он почти целиком виден и остаётся в поле зрения четверть
  секунды. Одновременно живыми бывают не больше двух.
- Предпросмотр, который ушёл далеко за пределы экрана, возвращается к статичному изображению,
  и это освобождает его страницу или видео.
- Видео ставятся на паузу, пока их не видно, а пока вкладка находится в фоне, всё ждёт.
- Тем, кто просит меньше движения или экономию трафика, показываются только статичные изображения.

Вот что это даёт на 300 проектах при прокрутке всего списка с постоянной скоростью, в сравнении
с загрузкой всего сразу и с ленивой загрузкой браузера:

| | Загрузить всё | Ленивая загрузка браузера | Планировщик (этот сайт) |
|---|---|---|---|
| Загружено при открытии | 38,6 МБ | 12,7 МБ | 0,47 МБ |
| Живых предпросмотров одновременно | 75 | 75 | 2 |
| Узлы DOM, максимум | 29 037 | 29 037 | 6 763 |
| Куча JS, максимум | 31,8 МБ | 29,1 МБ | 3,6 МБ |

[Бенчмарк](bench/README.ru.md#the-builds-page) тоже измеряет это на вашем собственном компьютере.

## <a id="how-it-works"></a>Как это устроено

Сайт генерируется, а не поддерживается вручную. Каждый принятый пулреквест представлен одним
небольшим markdown-файлом в `data/entries/`. `bin/site_data.py` читает эти файлы и записывает
`data/contributions.json`, а `bin/build_pages.py` встраивает эти данные в три страницы, поэтому
каждая страница загружается без запросов, кроме таблицы стилей и шрифта. `bin/deploy.py` публикует
собранные страницы на GitHub Pages. Число звёзд каждого репозитория хранится в одном месте,
в `data/stars.json`, а `bin/refresh_stars.py` получает все эти числа с GitHub, поэтому ни одно
число не копируется в запись (entry) и не расходится с настоящим.

- Ни фреймворка, ни инструментов сборки. Нужны только Python и браузер.
- Три темы (theme) переключаются образцами цвета в правом верхнем углу и построены на
  пользовательских свойствах CSS.
- Генеративные SVG-фоны рисуются прямо в браузере. Это зацепленные шестерёнки на главной странице
  (home page), git-граф слияний за реестром и чертёжная синька за страницей проектов.
- На каждой странице действует Content-Security-Policy, а каждый URL, пришедший из данных,
  проверяется до того, как попадёт в `href`.

## <a id="run-it"></a>Запуск

```
python3 bin/site_data.py        # записи в data/contributions.json
python3 bin/build_pages.py      # данные в три страницы в site/
python3 -m http.server --directory site
```

Затем откройте http://localhost:8000.

## <a id="tests"></a>Тесты

```
python3 -m unittest discover -s tests
```

Тесты покрывают пайплайн и страницы.

- Пересборка воспроизводима, а статистика имеет правильную структуру.
- Новая запись увеличивает порядковый номер и попадает в результат.
- Собранные страницы содержат усиленные настройки безопасности и виртуализированный список.
- Страница проектов загружает предпросмотры через планировщик, а проекты упорядочены по звёздам.
- Оба бенчмарка по-прежнему собирают свои страницы из текущих шаблонов.
- Каждый перевод соответствует своему английскому оригиналу.

## <a id="layout"></a>Структура

```
bin/     the pipeline, reads entries, builds pages, deploys
data/    one markdown file per merged PR, plus the per-repo star counts, the builds and the featured picks
site/    the three page templates, the shared stylesheet and script, the built output
bench/   the reproducible performance benchmarks and the server that measures the builds page
tests/   the pipeline tests
```
