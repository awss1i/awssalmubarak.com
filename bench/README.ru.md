## <a id="the-contributions-ledger"></a>Реестр вкладов

Реестр вкладов (contributions ledger) использует виртуализированный список. В DOM находятся только
строки рядом с областью просмотра (viewport), пулреквесты репозитория создаются только тогда, когда
вы его раскрываете, а поиск использует дебаунс (debounce) и фильтрует данные, вместо того чтобы
перестраивать страницу. Этот бенчмарк сравнивает его с наивной реализацией (naive version), которая
рендерит все строки сразу.

### <a id="run-it"></a>Запуск

```
python3 bench/generate.py          # 2500 репозиториев, около 14 000 принятых PR
python3 bench/generate.py 5000     # или задайте свой размер
python3 -m http.server             # из корня репозитория
```

Затем откройте обе страницы и прочитайте баннер в верхней части каждой:

```
http://localhost:8000/bench/dist/naive.html
http://localhost:8000/bench/dist/virtual.html
```

Каждый баннер показывает число узлов DOM, время одного повторного рендеринга (re-render) всего
списка и время до интерактивности (time to interactive). Синтетические данные строятся
с фиксированным сидом, поэтому обе страницы описывают в точности один и тот же набор данных,
а настоящие записи (entry) в `data/` здесь не затрагиваются.

### <a id="what-i-measured"></a>Мои измерения

На 2500 репозиториях и 13 724 принятых пулреквестах (merged pull request):

| | Наивная реализация (рендерит всё) | Виртуализированный список (этот сайт) |
|---|---|---|
| Узлы DOM | 127 306 | 281 |
| Повторный рендеринг одной сортировки | 279 мс | 3 мс |
| Время до интерактивности | 534 мс | 312 мс |

Абсолютные числа зависят от вашего оборудования. Общая картина от него не зависит. Наивная
страница держит в DOM примерно в 450 раз больше узлов и выполняет повторный рендеринг примерно
в 85 раз медленнее. Кроме того, наивная версия перестраивала весь список при каждом нажатии
клавиши в поле поиска, тогда как настоящая страница выполняет постоянный объём работы, каким бы
большим ни стал набор данных.

## <a id="the-builds-page"></a>Страница проектов

Страница проектов показывает предпросмотр каждого проекта, а живой предпросмотр (live preview)
является целой веб-страницей. Её планировщик медиа сначала показывает каждый предпросмотр как
статичное изображение (still image), делает его живым только тогда, когда он почти целиком виден,
держит живыми не больше двух одновременно и возвращает предпросмотр к статичному изображению,
когда тот уходит далеко за пределы экрана.

`bench/builds.py` генерирует 300 синтетических проектов, которые по очереди используют четыре вида
предпросмотра, доступных странице: изображение терминала, статичное изображение, живую страницу
и видео. Он прогоняет их через настоящий шаблон страницы проектов тремя способами:

- загрузка всего сразу
- ленивая загрузка (lazy loading) браузера, которая не умеет лениво загружать видео, поэтому каждое
  видео начинает загружаться при открытии страницы
- планировщик медиа, который и использует сайт

Каждый URL медиафайла уникален, поэтому кэш браузера не может скрыть ни одну загрузку.

### <a id="run-the-builds-benchmark"></a>Запуск бенчмарка проектов

```
python3 bench/builds.py            # 300 проектов
python3 bench/builds.py 600        # или задайте свой размер
python3 bench/serve.py             # раздаёт корень репозитория на порту 8000
```

Затем откройте каждую страницу в Chrome:

```
http://127.0.0.1:8000/bench/dist/builds-eager.html
http://127.0.0.1:8000/bench/dist/builds-lazy.html
http://127.0.0.1:8000/bench/dist/builds-scheduled.html
```

Через секунду после загрузки каждая страница прокручивает свой список сверху вниз со скоростью
1200 пикселей в секунду, а затем показывает вверху баннер с тем, во что это обошлось. Добавьте
к адресу `?manual`, чтобы прокручивать страницу самостоятельно.

Здесь `bench/serve.py` заменяет `python3 -m http.server`, потому что числа зависят от трёх вещей,
которых встроенный сервер не делает. Он отключает кэширование, поэтому каждый прогон загружает всё
заново. Он отвечает на запросы диапазонов (range requests) так же, как GitHub Pages, потому что
браузеры загружают видео частями. И он считает каждый отправленный байт. Собственные измерения
браузера не видят, что живой предпросмотр загружает внутри своего фрейма, и не видят видео,
загрузка которого оборвалась.

### <a id="what-i-measured-on-the-builds-page"></a>Мои измерения на странице проектов

На 300 проектах, по 75 каждого вида. В таблице медиана трёх прогонов каждой страницы. Прогоны
выполнялись в Chromium 153 из Playwright в новом режиме headless, с окном 1440 на 900, на AMD
Ryzen 7 255 под Linux.

| | Загрузить всё | Ленивая загрузка браузера | Планировщик (этот сайт) |
|---|---|---|---|
| Загружено при открытии | 38,6 МБ за 451 запрос | 12,7 МБ за 78 запросов | 0,47 МБ за 4 запроса |
| Загружено после прокрутки всего списка | 48,7 МБ | 48,7 МБ | 38,6 МБ |
| Живых предпросмотров одновременно, максимум | 75 | 75 | 2 |
| Узлы DOM, максимум | 29 037 | 29 037 | 6 763 |
| Долгие кадры анимации во время прокрутки | 7 | 3 | 0 |
| Куча JS, максимум | 31,8 МБ | 29,1 МБ | 3,6 МБ |

Открытие страницы обходится планировщику примерно в 80 раз дешевле, чем загрузка всего сразу,
и в 27 раз дешевле, чем ленивая загрузка браузера, а живых предпросмотров остаётся два, каким бы
длинным ни был список. Страница с ленивой загрузкой всё равно загружает каждое видео при открытии
и никогда не выгружает живую страницу, поэтому к концу прокрутки она держит столько же, сколько
страница, которая загрузила всё сразу.

Несколько замечаний к таблице:

- Долгий кадр анимации (long animation frame) является кадром, который занял больше 50 мс.
  Chromium в режиме headless рисует без настоящего экрана, поэтому эта метрика считает медленную
  работу страницы, а не пропущенные кадры, которые вы бы увидели. Она сильнее всего менялась между
  прогонами, от 0 до 66 у ленивой загрузки браузера.
- Число узлов DOM включает документ каждого живого предпросмотра, но не содержимое изображения
  или видео.
- Chrome сам ставит на паузу беззвучное видео вне области просмотра, поэтому на каждой странице
  одновременно играло не больше одного видео. Отличие планировщика в работе с видео в том, что он
  не загружает видео, пока оно не понадобится.
