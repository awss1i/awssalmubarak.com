## <a id="the-contributions-ledger"></a>コントリビューション台帳

コントリビューションのページは、リストを仮想化しています。DOM に置くのはビューポート付近の行だけで、リポジトリのプルリクエストはそのリポジトリを展開したときに初めて組み立てます。検索にはデバウンスをかけ、ページを組み立て直すのではなくデータを絞り込みます。このベンチマークでは、すべての行を一度に描画する単純な版と比べます。

### <a id="run-it"></a>実行方法

```
python3 bench/generate.py          # リポジトリ 2500 件、マージ済みの PR 約 14,000 件
python3 bench/generate.py 5000     # またはサイズを自分で指定
python3 -m http.server             # リポジトリのルートで実行
```

次に、両方のページを開き、それぞれの上部にあるバナーを確認します。

```
http://localhost:8000/bench/dist/naive.html
http://localhost:8000/bench/dist/virtual.html
```

各バナーには、DOM ノード数、リスト全体を 1 回再レンダリングするのにかかる時間、操作可能になるまでの時間（time to interactive）が表示されます。合成データは固定のシードを使うので、2 つのページはまったく同じデータセットを表しています。また、ここでの処理が `data/` にある実際のエントリーに触れることはありません。

### <a id="what-i-measured"></a>私の測定結果

リポジトリ 2,500 件、マージ済みのプルリクエスト 13,724 件での結果です。

| | 単純な実装（すべて描画） | 仮想化（このサイト） |
|---|---|---|
| DOM ノード数 | 127,306 | 281 |
| 並べ替え 1 回分の再レンダリング | 279 ms | 3 ms |
| 操作可能になるまでの時間 | 534 ms | 312 ms |

数値そのものはハードウェアによって変わりますが、傾向は変わりません。単純な版のページは DOM に約 450 倍のノードを持ち、再レンダリングは約 85 倍遅くなります。さらに単純な版では、検索ボックスでキーを押すたびにリスト全体を組み立て直していました。一方、実際のページの処理量は、データセットがどれだけ大きくなっても一定です。

## <a id="the-builds-page"></a>ビルドのページ

ビルドのページにはすべてのビルドのプレビューを表示していて、ライブプレビュー（live preview）は Web ページ 1 つ分まるごとです。メディアスケジューラーは、どのプレビューも最初は静止画（still image）として表示し、大部分が画面に入ってから初めてライブにします。同時にライブにするのは最大 2 つで、遠くまでスクロールされたプレビューは静止画に戻します。

`bench/builds.py` は、ターミナルの画像、静止画、ライブのページ、動画という、ページが表示できる 4 種類のプレビューを順に繰り返す合成のビルドを 300 件生成します。そしてそれらを、実際のビルドのテンプレートで次の 3 通りに描画します。

- すべてを一度に読み込む
- ブラウザーの遅延読み込み（lazy loading）。動画は遅延読み込みできないので、ページを開いた時点ですべての動画のダウンロードが始まります。
- メディアスケジューラー。このサイトで実際に使っているものです。

メディアの URL はすべて異なるので、ブラウザーのキャッシュでダウンロードが隠れることはありません。

### <a id="run-the-builds-benchmark"></a>ビルドのベンチマークの実行方法

```
python3 bench/builds.py            # ビルド 300 件
python3 bench/builds.py 600        # またはサイズを自分で指定
python3 bench/serve.py             # リポジトリのルートをポート 8000 で配信
```

次に、それぞれのページを Chrome で開きます。

```
http://127.0.0.1:8000/bench/dist/builds-eager.html
http://127.0.0.1:8000/bench/dist/builds-lazy.html
http://127.0.0.1:8000/bench/dist/builds-scheduled.html
```

各ページは読み込みから 1 秒後に、リストを上から下まで毎秒 1,200 ピクセルでスクロールし、そのあと上部のバナーにかかったコストを表示します。自分でスクロールしたいときは、アドレスに `?manual` を付けてください。

ここで `python3 -m http.server` の代わりに `bench/serve.py` を使うのは、数値が、組み込みのサーバーにはない 3 つの働きに左右されるからです。キャッシュを無効にするので、実行のたびにすべてを改めてダウンロードします。GitHub Pages と同じようにレンジリクエストに応答します。ブラウザーは動画を分割して取得するためです。そして、送ったバイト数をすべて数えます。ブラウザー自身の計測では、ライブプレビューがフレームの中でダウンロードしたものや、途中で打ち切られた動画が見えません。

### <a id="what-i-measured-on-the-builds-page"></a>ビルドのページでの私の測定結果

ビルド 300 件（各種類 75 件）で、各ページを 3 回ずつ実行した中央の値です。Playwright の Chromium 153 を新しいヘッドレスモードで使い、ウィンドウは 1440 × 900、マシンは Linux を動かす AMD Ryzen 7 255 です。

| | すべてを読み込む | ブラウザーの遅延読み込み | スケジューラー（このサイト） |
|---|---|---|---|
| 開いたときのダウンロード量 | 38.6 MB（リクエスト 451 件） | 12.7 MB（リクエスト 78 件） | 0.47 MB（リクエスト 4 件） |
| すべてスクロールした後のダウンロード量 | 48.7 MB | 48.7 MB | 38.6 MB |
| 同時に動くライブプレビューの最大数 | 75 | 75 | 2 |
| DOM ノード数の最大値 | 29,037 | 29,037 | 6,763 |
| スクロール中の長いアニメーションフレーム | 7 | 3 | 0 |
| JS ヒープの最大値 | 31.8 MB | 29.1 MB | 3.6 MB |

ページを開くときのコストは、スケジューラーではすべてを読み込む版の約 80 分の 1、ブラウザーの遅延読み込みの 27 分の 1 です。また、リストがどれだけ長くなっても、ライブプレビューは 2 つのままです。遅延読み込みのページは、開いた時点ですべての動画をダウンロードし、ライブのページを一度も解放しません。そのため、スクロールを終える頃には、すべてを一度に読み込んだページと同じだけのものを抱えています。

表を読むときに知っておいてほしい点がいくつかあります。

- 長いアニメーションフレーム（long animation frame）とは、50 ms より長くかかったフレームのことです。ヘッドレスの Chromium は実際の画面なしで描画するので、これは目に見えるフレーム落ちではなく、ページ上の遅い処理を数えています。実行ごとのばらつきが最も大きい値で、ブラウザーの遅延読み込みでは 0 から 66 まで変わりました。
- DOM ノード数には、すべてのライブプレビューのドキュメントが含まれますが、画像や動画の内部は含まれません。
- Chrome は、画面外にあるミュートされた動画を自分で一時停止します。そのため、どのページでも同時に再生された動画は最大 1 本でした。動画についてのスケジューラーの違いは、必要になるまでダウンロードしないことです。
