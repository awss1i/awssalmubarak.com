<p align="center">이 사이트의 두 페이지는 담는 양이 아무리 많아도 빠르게 동작하도록 만들었습니다.
기여 페이지는 목록을 가상 리스트(virtualized list)로 렌더링하고, 빌드(builds) 페이지는 미디어
스케줄러(media scheduler)를 통해 미리보기를 로드합니다. 이 폴더를 사용하면 두 페이지를 같은 페이지의
더 단순한 버전과 비교해, 직접 사용하는 컴퓨터에서 측정할 수 있습니다.</p>

## <a id="the-contributions-ledger"></a>기여 기록

기여 페이지는 목록을 가상 리스트로 렌더링합니다. 뷰포트(viewport) 근처의 행만 DOM에 들어 있고,
저장소의 풀 리퀘스트는 그 저장소를 펼칠 때만 만들어지며, 검색은 디바운스(debounce)를 적용하고 페이지를
다시 만드는 대신 데이터를 필터링합니다. 이 벤치마크는 모든 행을 한꺼번에 렌더링하는 단순 구현
버전과 비교합니다.

### <a id="run-it"></a>실행하기

```
python3 bench/generate.py          # 저장소 2500개, 병합된 PR 약 14,000개
python3 bench/generate.py 5000     # 또는 원하는 크기를 직접 지정
python3 -m http.server             # 저장소 루트에서 실행
```

그런 다음 두 페이지를 열고 각 페이지 상단의 배너를 확인하세요.

```
http://localhost:8000/bench/dist/naive.html
http://localhost:8000/bench/dist/virtual.html
```

각 배너에는 DOM 노드 수, 목록 전체를 한 번 재렌더링(re-render)하는 데 걸린 시간, 상호작용 가능 시간(time to interactive)이 표시됩니다. 합성 데이터는 고정된 시드를 사용하므로 두 페이지는 정확히 같은 데이터 세트를 나타내며, 여기서는 `data/`의 실제 항목(entry)을 전혀 건드리지 않습니다.

### <a id="what-i-measured"></a>제가 측정한 결과

저장소 2,500개, 병합된 풀 리퀘스트(merged pull request) 13,724개로 측정했습니다.

| | 단순 구현(모두 렌더링) | 가상 리스트(이 사이트) |
|---|---|---|
| DOM 노드 | 127,306 | 281 |
| 정렬 1회 재렌더링 | 279 ms | 3 ms |
| 상호작용 가능 시간 | 534 ms | 312 ms |

절대적인 숫자는 하드웨어에 따라 달라지지만, 전체적인 경향은 달라지지 않습니다. 단순 구현 페이지는 DOM에 노드를 약 450배 더 많이 담고 있고 재렌더링은 약 85배 느립니다. 또 단순 구현 버전은 검색 상자에 키를 누를 때마다 목록 전체를 다시 만들었지만, 실제 페이지는 데이터 세트가 아무리 커져도 일정한 양의 작업만 합니다.

## <a id="the-builds-page"></a>빌드 페이지

빌드 페이지는 모든 빌드의 미리보기를 보여 주고, 라이브 미리보기(live preview)는 웹 페이지 하나
전체입니다. 미디어 스케줄러는 모든 미리보기를 정지 이미지(still image)로 시작하고, 대부분 화면에
들어왔을 때만 라이브로 바꾸며, 한 번에 라이브인 미리보기를 최대 두 개로 유지하고, 멀리 스크롤되어
벗어난 미리보기는 정지 이미지로 되돌립니다.

`bench/builds.py`는 페이지가 보여 줄 수 있는 네 가지 미리보기, 즉 터미널 이미지, 정지 이미지, 라이브
페이지, 동영상을 번갈아 쓰는 합성 빌드 300개를 만듭니다. 그리고 실제 빌드 템플릿으로 세 가지 방식의
페이지를 렌더링합니다.

- 모든 것을 한꺼번에 로드하는 방식
- 브라우저의 지연 로딩(lazy loading). 동영상은 지연 로딩할 수 없으므로 페이지를 여는 순간 모든
  동영상의 다운로드가 시작됩니다.
- 미디어 스케줄러. 이 사이트가 실제로 쓰는 방식입니다.

모든 미디어 URL은 서로 다르므로 브라우저 캐시가 다운로드를 숨길 수 없습니다.

### <a id="run-the-builds-benchmark"></a>빌드 벤치마크 실행하기

```
python3 bench/builds.py            # 빌드 300개
python3 bench/builds.py 600        # 또는 원하는 크기를 직접 지정
python3 bench/serve.py             # 포트 8000에서 저장소 루트를 제공
```

그런 다음 Chrome에서 각 페이지를 여세요.

```
http://127.0.0.1:8000/bench/dist/builds-eager.html
http://127.0.0.1:8000/bench/dist/builds-lazy.html
http://127.0.0.1:8000/bench/dist/builds-scheduled.html
```

각 페이지는 로드되고 1초 뒤에 목록을 위에서 아래까지 초당 1,200픽셀로 스크롤한 다음, 그 비용을 상단의 배너에 표시합니다. 주소 끝에 `?manual`을 붙이면 직접 스크롤할 수 있습니다.

여기서는 `python3 -m http.server` 대신 `bench/serve.py`를 씁니다. 측정 결과가 내장 서버가 하지 않는 세 가지에 달려 있기 때문입니다. 이 서버는 캐시를 끄므로 매번 모든 것을 다시 다운로드합니다. GitHub Pages처럼 범위 요청에 응답합니다. 브라우저가 동영상을 조각으로 나눠 가져오기 때문입니다. 그리고 보내는 바이트를 모두 셉니다. 브라우저 자체의 타이밍은 라이브 미리보기가 자기 프레임 안에서 다운로드한 것이나 중간에 끊긴 동영상을 보지 못합니다.

### <a id="what-i-measured-on-the-builds-page"></a>빌드 페이지에서 제가 측정한 결과

빌드 300개(종류별 75개)로, 각 페이지를 세 번씩 실행한 결과의 중간값입니다. Playwright의 Chromium 153을 새 헤드리스 모드로, 1440 x 900 창에서, Linux를 쓰는 AMD Ryzen 7 255에서 실행했습니다.

| | 모두 로드 | 브라우저 지연 로딩 | 스케줄러(이 사이트) |
|---|---|---|---|
| 열 때 다운로드한 양 | 38.6 MB, 요청 451개 | 12.7 MB, 요청 78개 | 0.47 MB, 요청 4개 |
| 전부 스크롤한 뒤 다운로드한 양 | 48.7 MB | 48.7 MB | 38.6 MB |
| 동시에 라이브인 미리보기, 최대 | 75 | 75 | 2 |
| DOM 노드, 최대 | 29,037 | 29,037 | 6,763 |
| 스크롤하는 동안의 긴 애니메이션 프레임 | 7 | 3 | 0 |
| JS 힙, 최대 | 31.8 MB | 29.1 MB | 3.6 MB |

스케줄러는 페이지를 열 때의 비용이 모두 로드하는 방식보다 약 80배, 브라우저의 지연 로딩보다 27배 적고, 목록이 아무리 길어도 라이브 미리보기는 두 개로 유지됩니다. 지연 로딩 페이지는 여전히 페이지를 열 때 모든 동영상을 다운로드하고 라이브 페이지를 절대 언로드하지 않으므로, 스크롤이 끝날 무렵에는 모든 것을 한꺼번에 로드한 페이지만큼을 담고 있습니다.

표를 읽을 때 알아 둘 점이 몇 가지 있습니다.

- 긴 애니메이션 프레임(long animation frame)은 50 ms보다 오래 걸린 프레임입니다. 헤드리스 Chromium은 실제 화면 없이 그리므로, 이 값은 눈에 보이는 프레임 끊김이 아니라 페이지의 느린 작업을 셉니다. 실행할 때마다 가장 많이 달라진 값으로, 브라우저의 지연 로딩에서는 0에서 66까지 나왔습니다.
- DOM 수에는 모든 라이브 미리보기의 문서가 포함되지만, 이미지나 동영상 내부는 포함되지 않습니다.
- Chrome은 화면 밖에 있는 음소거된 동영상을 스스로 일시정지하므로, 모든 페이지에서 한 번에 재생된 동영상은 최대 하나였습니다. 동영상에 대한 스케줄러의 차이는 필요할 때까지 동영상을 다운로드하지 않는다는 점입니다.
